## 0. 촬영 시작 전 — DB 초기화 (매 촬영 시작 시, 재촬영 시작 시 모두 실행)

`/actions/new?requestId=N`은 열릴 때마다 새 Action 행을 만드는 알려진(의도적으로
남겨둔) 동작이다. 리허설이나 NG로 이 화면을 다시 열면 DRAFT 액션이 쌓이고, 같은
흐름을 두 번 완주하면 이름이 같은 ACTIVE 액션이 두 개가 되어 장면 8의 Tool 목록에
중복으로 뜬다. 코드로 막지 않고 **아래 절차로 막는다.**

**아래 절차는 최초 촬영 시작 전뿐 아니라, NG 이후 재촬영(re-take)을 시작하는
시점마다 실행한다.** "한 번만 하면 되는 준비 작업"이 아니라 매 테이크의 리셋 버튼이다.

```bash
# 1) DB 파일 자체를 지운다 — 세션 번호가 #1부터 다시 시작되고 중복 액션이 사라진다
rm -f apps/backend/data/dev.db

# 2) 포트를 쥐고 있는 낡은 프로세스를 확실히 죽인다.
#    pid 파일(/tmp/backend.pid)에 의존하지 않는다 — 파일이 가리키는 프로세스가
#    이미 죽었거나 다른 프로세스로 바뀌어 있을 수 있고, 그러면 이전 커밋의
#    코드를 그대로 물고 있는 uvicorn이 8000번 포트에 남아 조용히 낡은 라우트를
#    서빙한다(콘솔이 404를 내는 원인이었다). lsof로 실제 점유 프로세스를 찾아 죽인다.
lsof -ti :8000 | xargs -r kill

# 3) 백엔드를 새로 기동한다 — 기동 시 init_db() + seed()가 실행되어
#    테이블 생성과 시드 데이터 삽입이 자동으로 끝난다
cd apps/backend && .venv/bin/uvicorn app.main:app --port 8000
```

세션 번호가 `#1`이 되어 화면에 자연스럽게 나오는 부수 효과도 있다 — 이 점을
장면 4→5 전환에서 대사로 활용해도 된다.

### 촬영 전 최종 점검 (Pre-flight, 매 테이크 직전)

1. **백엔드가 최신 코드를 서빙하는지 확인한다.** pid나 로그를 신뢰하지 말고
   라우트 존재 자체를 확인한다:
   ```bash
   curl -s http://localhost:8000/openapi.json | python3 -c \
     "import json,sys; print('/api/projects/{project_id}/llm-test' in json.load(sys.stdin)['paths'])"
   ```
   `True`가 아니면 위 §0의 2)~3)을 다시 수행한다 — 낡은 프로세스가 여전히
   포트를 쥐고 있다는 뜻이다.

2. **`.env`가 로드되는지 확인한다.** 값은 화면(카메라)에 절대 띄우지 않고
   네 개의 키가 "있다/없다"만 확인한다:
   ```bash
   cd apps/backend && .venv/bin/python -c \
     "from dotenv import load_dotenv; import os, pathlib; \
      load_dotenv(pathlib.Path('.env')); \
      keys=['AZURE_OPENAI_API_KEY','AZURE_OPENAI_ENDPOINT','AZURE_OPENAI_API_VERSION','AZURE_OPENAI_DEPLOYMENT']; \
      print({k: bool(os.environ.get(k)) for k in keys})"
   ```
   네 값이 모두 `True`여야 한다. `apps/backend/.env`는 git-ignore 대상이며
   **어떤 경우에도 커밋하지 않는다.**

3. 관리자 화면(`apps/admin`, 5173번 포트)이 떠 있는지, `http://localhost:5173/console`이
   에러 없이 열리는지 확인한다.

4. 실거래가 사이트(`https://rt.molit.go.kr`)와 Azure OpenAI 호출은 모두 **실측·과금
   대상**이다. 리허설 중 반복 호출을 최소화하고, 최종 테이크 직전 1회만 정식으로 돌린다.

## 리허설 기록 (Step 3 실측)

전체 흐름(장면 1~10)을 리셋된 DB에서 처음부터 한 번 완주하며 다음을 확인했다:

- 지도 확대/축소 버튼 클릭은 `interactionId`로 정상 연결된다. 드래그는 연결되지
  않는 것이 재확인됨 — 촬영 시 반드시 클릭/버튼 조작만 사용한다.
- 세션 상세(장면 5)에서 `accesLog.do`는 항상 최하위(점수 3)로 나타난다.
  `getMarker.do`(★9)와 `getCenterLedCdPnu.do`(9)는 동점이라 순서가 고정되지
  않으므로, 화면에서 행을 지목할 때는 순서가 아니라 URL로 말한다.
- 대상 사이트(WAF)는 `PRESERVED_HEADERS`(Referer, X-Requested-With, Accept,
  User-Agent, Content-Type)를 그대로 재현하면 막히지 않았다. 헤더가 하나라도
  빠지면 400이 재현될 수 있으므로 장면 10 직전에 실행 게이트웨이가 실제로
  이 헤더들을 싣는지 `apps/backend/app/services/executor.py`의 동작을 신뢰한다.

## 재촬영(re-take) 시 체크리스트

NG가 나서 특정 장면부터 다시 찍을 때, 어느 장면부터 다시 시작하든
**§0의 DB 초기화 3단계를 먼저 실행한다.** 특히:

- 장면 6~7(액션 편집 화면)을 한 번이라도 열었다면 DRAFT 액션이 이미 하나
  이상 쌓여 있다 — §0을 건너뛰고 이어서 찍으면 장면 8의 Tool 목록에 중복이
  보일 수 있다.
- §0을 실행하면 세션 번호가 다시 `#1`부터 시작하고, 시드 액션
  "아파트 단지 마커 조회"가 항상 ACTIVE 상태로 정확히 하나만 존재하는
  상태로 돌아온다. 개발 중 DB에 남아있던 `test`라는 이름의 액션(및 id 2의
  액션)은 이 리셋으로 완전히 사라진다 — 화면에 `test`가 노출될 일이 없다.
