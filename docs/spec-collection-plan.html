계층 원칙 — 3종은 동일 depth의 수집 방식이고, "기관 포털"은 그중 포털 공개 기반 수집의 대상 목록일 뿐이다. 트래픽 기반은 대상이 특정 사이트가 아니므로 하위 목록을 갖지 않는다.

1. 통합 전략 — 왜 이 구조인가

mcp-studio의 기존 흐름:

Project→RecordingSession→NetworkRequest(후보)→Action→LLM 콘솔

수집 엔진을 별도 시스템으로 나누지 않는다. 세션에 kind를 붙여 후보 생성 방식만 분기하고, 그 뒤는 전부 공유한다.

Project→Session kind→ NetworkRequest SpecOperation (Phase 2) →Action→LLM 콘솔 (공통)
이점 — Action·tool_registry·executor·LLM 콘솔·마스킹을 손대지 않는다. 신규 코드는 "HTML → 후보" 파서 하나로 수렴하고, 사용자에게도 학습할 흐름이 하나로 유지된다. 문서 기반(Phase 2)도 같은 자리에 후보 생성기만 추가하면 끝난다.

3. 파서 — 포털 공개 기반 수집의 심장

data.go.kr 상세페이지는 서버 렌더(SSR)이고 명세가 정형 표로 들어있다. 실제 페이지에서 확인한 구조:

// 확인 완료 서비스URL http://apis.data.go.kr/B552584/ArpltnInforInqireSvc 오퍼레이션 .../getMinuDustFrcstDspth ← 상세기능 5개 요청변수 표 (6컬럼 완전 정형) 항목명(국문) | 항목명(영문) | 항목크기 | 항목구분 | 샘플데이터 | 항목설명 서비스키 | serviceKey | 4 | 필 | - | 공공데이터포털에서 받은 인증키 조회 날짜 | searchDate | 10 | 옵 | 2020-11-14 | 통보시간 검색

취득 방식 — 서버가 크롤링하지 않는다
robots.txt에 목록 페이지(/tcs/dss/selectDataSetList.do)가 Disallow로 명시돼 있다. 따라서 확장이 "사용자가 이미 연 페이지"의 DOM을 백엔드로 보내고 백엔드는 파싱만 한다. 서버발 자동 순회 크롤은 구현하지 않는다. 파싱 로직을 백엔드에 두는 이유는 pytest로 빠르게 검증하기 위함이다.
포털 확장 설계 — 파서는 PARSERS = {"data.go.kr": parse_datagokr, ...} 레지스트리 형태로 둔다. KOSIS·서울광장을 추가할 때 함수 하나만 등록하면 되고 상위 흐름은 불변이다.

4. UI/UX 통합 설계 ★

사용자가 세 개의 도구를 배우는 것처럼 느끼면 실패다. 같은 뼈대 위에서 맥락에 따라 라벨과 강조만 바뀌는 하나의 흐름으로 설계한다.

4-1. 공통 5단계 스테퍼 — 라벨만 맥락화

단계 트래픽 기반 포털 공개 기반 문서 기반 (P2)
STEP 1기록 시작페이지 열기문서 업로드
STEP 2클릭 기록명세 감지텍스트 추출
STEP 3API 분석 (점수화)명세 파싱 (오퍼레이션)LLM 구조화
STEP 4액션 생성 — 공통
STEP 5테스트 (LLM 콘솔) — 공통
핵심 — 뒤 2단계가 물리적으로 동일한 화면이다. 사용자는 "수집 방식만 다르고 그 다음은 똑같다"를 화면으로 학습한다.

UX 원칙 — 두 버튼을 항상 함께 보여주되, 페이지 판정에 따라 주/보조만 뒤바꾼다. 모드를 미리 고르게 하지 않으므로 "어느 기능을 써야 하나" 고민할 일이 없다. 문서 기반은 파일 업로드라 사이드패널이 아닌 관리자 화면에 배치(Phase 2).

4-3. 관리자 — 수집 엔진 화면 (신규)

§0의 3종 카드 레이아웃을 그대로 관리자 /sources 화면으로 구현한다. 포털 공개 카드 하위에만 기관 포털 목록이 붙고, 각 행은 동작/준비중이 점 표시로 구분된다.

더미 표기 원칙 — "준비중"은 흐린 처리 + 회색 점으로 명시하고 클릭 시 "Phase 2 예정" 안내만 띄운다. 화면에 뜨는 것 중 동작하는 것과 아닌 것이 구분되어야 심사에서 신뢰를 잃지 않는다.

4-4. 세션 목록·상세 — kind 분기

/projects/1 — 수집 세션
세션수집 방식후보액션

세션 상세는 kind로 분기 — traffic이면 기존 점수판(★9 / 로그 −5), portal이면 오퍼레이션 목록(각 행에 파라미터 수·필수 수). 두 화면 모두 우측 액션 열은 [액션 만들기]로 동일.

4-5. 액션 목록 — 출처 배지로 혼합 노출

액션 목록에 수집 방식 배지를 달아 세 경로가 하나의 레지스트리로 수렴했음을 한 화면에서 보여준다. 시연 ACT4의 "통합 레지스트리" 장면이 이 화면이다.

5. 개발 단계

Phase 0 — 준비 0.5h

  • 이슈 생성 → feature/portal-spec-collection-issue 브랜치 (레포 컨벤션 준수)
  • 픽스처 저장: apps/backend/tests/fixtures/datagokr_airkorea.html (이미 확보한 1회 조회분)

Phase 1 — 파서 + 모델 3h 절단 불가

  • app/services/spec_parser.py — PARSERS 레지스트리 + parse_datagokr(html, url)
    서비스URL·상세기능·요청변수표·출력결과표 추출. 표준 라이브러리 re+html로 충분(신규 의존성 회피 — 레포 규칙)
  • app/models.py — SpecOperation 신규, RecordingSession.kind, Project.credentials
  • tests/test_spec_parser.py — 픽스처 회귀 (오퍼레이션 5개·필수 파라미터·타입 추론·표 없는 페이지)

Phase 2 — API + 액션 변환 2h 절단 불가

  • app/routers/spec.py
    POST /api/projects/{id}/spec-sessions — {url, html} 수신 → 파싱 → 세션(kind=portal)+SpecOperation 저장
    GET /api/recording-sessions/{id}/spec-operations — 후보 목록
  • app/services/schema_infer.py — build_action_spec_from_spec(op, ...) 추가
    기존 build_action_spec과 동일한 action_spec 형태를 만드는 게 요점. 그래야 tool_registry·executor 무수정
  • app/services/executor.py — llmEditable:false 파라미터에 Project.credentials 주입

Phase 3 — 확장 2h

  • extension/lib/spec-detect.ts — 페이지 판정 (URL 패턴 + "요청변수" 표 존재)
  • entrypoints/sidepanel/App.tsx — 감지 배지 + 주/보조 버튼 전환 (4-2)
  • entrypoints/content.ts — outerHTML 전송 경로 · background.ts — 백엔드 전송

Phase 4 — 관리자 화면 2h

  • admin/src/pages/SourceList.tsx — 수집 엔진 3종 화면(§0 레이아웃, 일러스트 포함)
  • admin/src/pages/SpecSessionDetail.tsx — 오퍼레이션 목록 + [액션 만들기]
  • SessionList.tsx · ActionList.tsx — kind/출처 배지
  • App.tsx 라우팅 · styles/app.css (CSS 단일 파일 규칙 준수, SVG는 컴포넌트 인라인)
  • 스테퍼 라벨 kind별 분기 (4-1)

Phase 5 — 통합 검증 · 시드 0.5h

  • 시드에 포털 공개 수집 세션 1건 추가 (첫 화면부터 두 방식이 섞여 보이도록)
  • E2E: 명세 페이지 → 수집 → 액션 → LLM 콘솔 질의 → 실호출 200
  • 기존 90개 테스트 회귀 확인

총 10h. 시간 부족 시 절단 순서 — ① Phase 4의 SourceList 일러스트 → ② 스테퍼 라벨 분기 → ③ 확장 UI(대신 관리자에서 URL 붙여넣기로 대체). Phase 1·2는 절단 불가.

⚠ 이번 작업에서 지킬 것

  • 서버발 자동 크롤 금지 — 확장이 보낸 "사용자가 연 페이지"만 파싱. 목록 페이지 자동 순회 미구현(robots Disallow 경로)
  • 레포 규칙 준수 — Python 3.10 문법 · 새 프런트엔드 의존성 금지 · CSS는 app.css 한 파일 · 주석/UI 문구 한국어 · window.confirm/alert 금지
  • 미구현을 숨기지 않음 — 준비중 포털·문서 기반 수집은 "준비중"으로 명시. 화면 숫자는 실제 데이터만
  • 기존 흐름 무파손 — kind 기본값 traffic. 트래픽 기반 경로 코드는 최소 수정
  • 호출 간격 — 기존 MIN_INTERVAL_SEC=1.0 유지(공공 서버 배려)
