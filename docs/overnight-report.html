1. 무엇이 달라졌나

어제까지

상세페이지를 한 장씩 열고 확장에서 수집 클릭.
게다가 포털은 상세기능을 목록에서 하나씩만 보여줘서, 한 서비스에 5개가 있으면 목록을 5번 바꿔야 했습니다.
25개를 모으려면 사람이 25번 이상 클릭.

지금

검색 주소 한 줄 붙여넣고 수집 시작 1번.
목록을 넘겨가며 서비스마다 상세기능을 전부 펼쳐 모읍니다.
사람이 누르는 건 2번 — 수집 시작, 전체 액션 만들기.

2. 어떻게 쓰나 (실제 순서)

1
수집 엔진 화면을 연다
왼쪽 메뉴 02 수집 엔진. 가운데 포털 공개 기반 수집 카드 안에 새 패널이 생겼습니다.
2
결과를 담을 프로젝트를 고른다
기본으로 “공공데이터포털 오픈API”가 잡힙니다. 이걸 안 보여주면 대기 API를 모았는데 실거래가 프로젝트에 들어가는 일이 생깁니다.
3
키워드 버튼을 누르거나 주소를 붙여넣는다
‘대기·미세먼지 / 날씨 / 교통 / 관광’ 버튼이 있고, 포털에서 직접 검색한 주소를 그대로 붙여넣어도 됩니다. 사용자가 건 필터도 그대로 유지됩니다.
4
개수를 고르고 “수집 시작”
10 / 20 / 30 / 50개. 진행률 막대와 함께 “지금 몇 개 모았고 몇 번째 서비스를 보고 있는지”가 실시간으로 갱신됩니다.
5
끝나면 “수집 결과 보기”
어느 기관의 어느 서비스에서 온 API인지, 파라미터가 몇 개고 필수가 몇 개인지 표로 보입니다.
6
“전체를 액션으로 만들기” 한 번
25개가 한꺼번에 MCP 도구가 됩니다. 다시 눌러도 중복이 생기지 않습니다.
수집 엔진 화면 — 가운데 카드에 새로 들어간 일괄 수집 패널. 프로젝트 선택 · 키워드 버튼 · 주소 · 개수 · 시작 버튼.
수집 결과 — “서비스 13개 · 오퍼레이션 25개” 요약과 전체를 액션으로 만들기 버튼. 각 줄 위에 어느 기관·어느 서비스인지 표시.
“전체를 액션으로 만들기” 결과 — MCP 도구 25개가 한 번에 생성됐고, 모두 ACTIVE 상태라 테스트 콘솔에서 바로 쓸 수 있습니다.

4. 심사 관점에서 제 판단

강함
편의성 — “주소 한 줄 → 클릭 2번 → MCP 도구 25개”는 시연에서 10초 만에 이해됩니다. 진행률이 실시간으로 움직여 살아 있다는 게 보이고, 결과 화면이 기관·서비스명을 보여줘 “무엇을 모았는지” 설명이 필요 없습니다.
강함
기술 구현 — 남들이 놓치는 두 지점을 실제로 뚫었습니다. ① 포털이 명세만 게시하고 실행하지 않는다는 점(트래픽 관측으로는 원천 불가) ② 상세기능이 ajax로 숨어 있다는 점. 둘 다 실제 사이트에서 검증했습니다.
강함
확장 가능성 — 파서를 PARSERS 목록에 함수 하나 추가하는 구조로 만들어서, KOSIS·서울 열린데이터광장은 함수 하나면 붙습니다. 화면에는 “준비중”으로 이미 자리를 잡아뒀습니다.
보완 여지
수집 성공률 — 43개 서비스를 훑어 11개에서 결과가 나왔습니다(약 26%). 포털에 등록만 되고 명세 표가 없는 서비스가 많아서인데, 화면에는 성공한 것만 보이므로 시연에 문제는 없습니다. 다만 “43개 중 11개”를 물어보면 솔직히 답해야 합니다.
보완 여지
속도 — 25개에 약 2분입니다. 공공 서버 배려로 요청 간 1초를 두기 때문인데, 이건 줄이지 않는 게 맞다고 봅니다. 시연에서는 미리 수집해 둔 결과를 보여주고, 수집은 30초 정도만 보여주다 넘기는 편성을 권합니다.
심사에서 이렇게 말씀하시면 좋겠습니다. “공공 API는 대부분 문서로만 공개되고 그 사이트에서 실행되지 않습니다. 그래서 화면을 엿듣는 방식으로는 원천적으로 못 잡습니다. 저희는 문서를 읽는 수집기를 따로 만들었고, 포털 검색 주소 한 줄이면 그 안의 API를 한꺼번에 MCP 도구로 만듭니다.”

5. 예의와 안전장치

남의 서버를 긁는 기능이라, 물어보면 답할 수 있게 다음을 넣었습니다.

장치내용
요청 간격 1초기존 실행기와 같은 기준. 25개에 2분이 걸리는 이유이자, 줄이지 않는 이유입니다.
상한 60개무제한 순회하지 않습니다. 화면에서는 최대 50개까지 고를 수 있습니다.
사용자 주도사람이 주소를 등록하고 버튼을 눌러야만 돕니다. 스케줄러도, 자동 재수집도 없습니다.
로그인 불필요비로그인으로 읽히는 공개 페이지만 봅니다. 계정·비밀번호를 다루지 않습니다.
인증키 은닉serviceKey 는 LLM에게 보여주지 않고 호출 직전에 넣습니다. 키가 없으면 호출 전에 막고 이유를 알려줍니다.

6. 만든 것 (파일 기준)

services/portal_crawler.py 신규목록 → 상세 → 상세기능 전부. 주소 정규화·페이징·중복 제거·간격 조절
services/crawl_runner.py 신규백그라운드 실행과 진행 상황 기록. 끝나면 세션·오퍼레이션으로 저장

tests/test_portal_crawler.py 신규주소 정규화·목록 파싱·상한 검증 8개
routers/spec.py 보강수집 시작·진행 조회 + 일괄 액션 생성(중복 건너뛰기 포함)
pages/SpecSessionDetail.tsx 보강서비스명 표시, 요약 줄, 전체 액션 버튼, 안내 문구 분기
models.py 보강CrawlJob 추가 (진행 상황 보관)

트래픽 기반 수집은 손대지 않았습니다. 기존 기록·액션·콘솔 경로 그대로입니다.

자동 테스트

139개 통과
(기존 대비 8개 추가). 남의 서버 상태에 좌우되는 테스트는 만들지 않았습니다 — 빨간불이 자주 켜지면 아무도 안 보게 되니까요.

실제 사이트 E2E

실제 data.go.kr 로 25개 수집 → 액션 25개 생성 → 재실행 시 중복 0 → 인증키 은닉 확인까지 끝까지 돌렸습니다.

실패 상황도 확인했습니다

다른 포털 주소 → "아직 공공데이터포털(data.go.kr) 주소만 수집할 수 있습니다" 개수 999 요청 → "한 번에 수집할 수 있는 최대 개수는 60개입니다" 결과 없는 키워드 → "수집된 API가 없습니다. 검색 결과가 있는 목록 URL인지 확인하세요" 없는 작업 조회 → "해당 수집 작업을 찾을 수 없습니다"

모두 한국어로 원인과 다음 행동을 알려줍니다. 심사 중 문제가 생겨도 화면만 보고 설명할 수 있습니다.

9. 제가 하지 않은 것 (판단 근거 포함)

안 한 것이유
수집 성공률 개선명세 표가 없는 서비스를 억지로 파싱하면 틀린 도구가 생깁니다. 성공한 것만 보여주는 편이 안전합니다.
속도 향상(병렬 요청)남의 서버에 대한 예의를 깨는 방향입니다. 시연은 편성으로 해결하는 게 맞습니다.
KOSIS·서울광장 파서구조는 이미 열어뒀습니다(PARSERS). 지금 넣으면 검증할 시간이 없어 “준비중”이 정직합니다.
수집 결과 자동 발행사람이 한 번은 확인하고 넘어가는 편이 낫습니다. 잘못 만든 도구가 조용히 발행되면 되돌리기 어렵습니다.
