## 산출 방식 (접근안 A — 승인됨)

마크다운 마스터 초안으로 내용을 확정한 뒤 python-docx로 지정 양식에 자동 이식한다.
검토·수정은 md에서 돌리고, docx 생성은 마지막에 한 번. 이식 스크립트가 양식을
깨뜨리면 수동 이식(접근안 C)으로 내려가는 퇴로를 둔다.

### 파일 구성

```
docs/report/
  interim-report.md        마스터 초안 (검토·수정 지점)
  assets/
    architecture.png       시스템 구성도 (신규 생성)
    capture-*.png          화면 캡처 (기존 5장 + 추가 촬영)
    metrics.md             정량 실측 원본 기록 (보고서 수치의 출처)
  build_docx.py            양식 이식 스크립트 (python-docx)
  중간결과보고서_최종.docx    제출본
```

python-docx는 스크래치패드 전용 venv에 설치한다 (백엔드 venv 오염 금지).

### 작업 순서

1. 참고자료 생성 — DB 리셋 → 백엔드·관리자 기동 → 테스트 스위트 실행 → 일괄 수집 실측 1회 → LLM 콘솔 실측 1~2회 → 화면 캡처 → 구성도 생성
2. md 초안 작성 (7장 전체, 실측·캡처 인용)
3. 사용자 검토 사이클
4. docx 이식 → Word/한컴에서 최종 확인

안전장치: 포털 일괄 수집 1회만(1초 간격·60건 상한·재시도 없음), Azure 호출 1~2회로
제한, 캡처 전 `.env`·인증키 노출 여부 확인.

## 장별 내용 설계

양식의 절 구조를 그대로 따른다. 각 절에 연계 평가항목이 명시돼 있으므로

**표지** — 프로젝트명은 구현제안서와 동일 표기. 일반 트랙 체크. 팀명·소속은 [확인 필요].

**1장 일반사항 (~2p)**
- 1.1~1.3 제안서의 기술명·변압기 비유·목적 승계
- 1.4 기술 동향: MCP 표준 확산·AI 에이전트 동향, 웹 조사로 근거 1~2건 보강
- 1.5 유사 기술 비교: mcp-use·Playwright 비교 표, 실제 구현 기준 차별점(수집 3경로·자동 스키마 추론·신뢰장치)으로 갱신
- 1.6 변경사항 표 (핵심 지점 — 솔직하되 합리적 의사결정으로):
  | 구분 | 제안서 | 변경 후 | 사유(요지) |
  |---|---|---|---|
  | 수집 방식 | VLM 시각 인지 자율 탐색 | Chrome 확장 기반 사용자 주도 기록 + 클릭-요청 상관관계 스코어링 | 실사용 흐름 관측이 명세 정확도가 높고 VLM 비용·불확실성 제거 |
  | 수집 범위 | 트래픽 단일 | 트래픽/포털 명세/문서(예정) 3경로 | 명세만 게시하는 공공 포털 대응 |
  | MCP 바인딩 | mcp-use 자동 배포 | function calling 도구 변환 선행, MCP 엔드포인트는 2차 기간 | 도구 정의 계층 선검증 |
  | 스택 | PostgreSQL·Redis·Celery·LangChain | SQLite·SQLModel·직접 호출 | 프로토타입 반복 속도 |
  | 배포 | On-prem Helm | Azure Container Apps | 심사·시연 접근성 |

**2장 핵심 기술 (~2.5p)**
- 2.1 문제(레거시 API 비정형·비문서화) → 아이디어(실행 관측 + 명세 파싱의 이중 역분석) → 구성요소 6개: 수집 3경로 / 후보 스코어링 / 스키마 추론(타입·예시값·WAF 헤더 보존) / 액션(세션 독립 값 복사) / 실행 게이트웨이(레이트리밋·인증키 주입·마스킹) / LLM 도구 변환
- 2.2 ①모델: Azure OpenAI function calling ②데이터 파이프라인: NetworkRequest→ActionSpec ③학습·튜닝 대신 도구 정의 엔지니어링(한국어 시스템 메시지 + `tool_choice=required` 실측 근거) ④추론·배포: FastAPI·ACA

**3장 개발 성과 (~5p, 최대 배점)**
- 3.1.2 주요기능 5개: ①트래픽 기반 기록(확장) ②포털 명세 수집(단건+일괄) ③스키마 추론·액션 변환 ④LLM 실행 게이트웨이 ⑤통합 관리자 콘솔
- 3.1.3 구성도 이미지 삽입
- 3.1.4 사전 구현 성과: 전 구간 파이프라인 완주 + 실측 수치 + ACA 배포
- 3.1.5 향후 계획: MCP 엔드포인트 표준화, 문서 기반 수집, HITL 인증 브릿지, API 토폴로지 그래프 — 제안서 미구현 항목을 2차 기간 계획으로 회수
- 3.2 기능별 상세: 개요/개발 현황(캡처 인용)/진척도 % — %는 산정 근거와 함께 제안, 사용자 확정
- 3.3.1 정량: 테스트 155개, 일괄 수집 25건/약 2분, 실행 응답 실측, 로그 API 최하위 랭킹 사례 — 재실측치로 갱신
- 3.3.2 혁신성: A2S 패러다임, 비침투적 연동, AI 에이전트 트렌드 정합
- 3.3.3 대표 실적: 사실대로 (배포 데모 등), 없는 것을 만들지 않음
- 3.3.4 신뢰성 (강점 절): 마스킹 3곳, 인증키 LLM 은닉, 호출 간격 1초, 응답 원문 미저장, 도구 강제 호출·example 주입으로 환각 억제, 실행 전 사용자 확인

## 참고자료 생성 설계

**구성도**: 코드 구조 기반 3계층(확장→백엔드→관리자) + 3경로 합류 흐름.
Mermaid 작성 후 이미지 렌더(스크래치패드에서 일회 실행, 레포 의존성 없음). 라벨 한국어.

**캡처** (demo-script §0 리셋 후 시드 상태, Playwright):
| 대상 | 용도 |
|---|---|
| `/sources` 수집 엔진 | 3.1.2 |
| 포털 명세 세션 상세 (시드 #3) | 3.2 |
| 액션 편집 (파라미터 추론 표) | 3.2 |
| LLM 콘솔 실행 결과 | 3.2 + 6장 |
| 일괄 수집 진행/결과 | 3.2 (실측과 동시 확보) |

**실측** (`assets/metrics.md`에 원본 기록):
- pytest 133 + vitest 22 + 타입체크 2종 — 통과 수·소요 시간
- 일괄 수집 1회 (미세먼지 25건 규모) — 소요·서비스/오퍼레이션 수·성공률
- LLM 콘솔 1~2회 — 도구 선택·파라미터 채움·응답 시간
- 트래픽 기록 경로는 확장 수동 조작이 필요하므로 기존 실측치(README·demo-script 리허설 기록) 인용, 출처 명시
